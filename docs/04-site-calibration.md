# Калибровки существующего сайта

## Зачем существует второй уровень

Обязательная учебная формула использует базовые GPU/CPU-факторы и множители опций. В текущем сайте часть лимитов исправляется по историческим тестам и сопоставимым профилям. Кроме того, для некоторых игр предусмотрены source-native пресеты с реальными настройками источника.

Сохраняйте `fps-edu-basic-v1` как отдельный проверяемый режим. Для калиброванного расширения используйте другое имя алгоритма. Целевая метрика — средний отрисованный FPS; она не становится минимальным FPS, 1% low или частотой с генерацией кадров. Прогноз по историческим данным не является замером конкретного собранного компьютера.

## Ручной сценарий с индексным вектором

В существующем `calculateFps` сначала формируются M, legacy GPU и legacy CPU. Затем для каждого компонента отдельно выбирается применимый лимит.

1. Ищется точная строка scenario-таблицы по `game_slug`, `resolution_key`, упорядоченному `setting_indexes` и `hardware_slug`. При совпадении её `fps` заменяет соответствующий компонентный лимит целиком. Повторно умножать его на M нельзя.
2. Если точной строки нет, проверяется native-домен: RT и upscale выключены; native 100%/1x также подходит для upscale. Обычные визуальные настройки могут иметь любые допустимые значения.
3. В native-домене GPU получает `legacyGpu × profile.multiplier`. Профиль берётся по игре, GPU и разрешению.
4. CPU получает `profile.base_fps × произведение profile.setting_multipliers[order][selectedIndex]`. Этот профиль привязан к игре и CPU, без отдельного ключа разрешения.
5. При отсутствии применимого профиля остаётся legacy-лимит.
6. Итог: один `min` двух компонентных лимитов и cap игры, затем одно округление.

Native GPU-прогноз дополнительно ограничивается точными якорями той же игры, GPU и разрешения. Сравниваются множители каждой визуальной настройки: если запрос не легче якоря по каждой настройке, его FPS не может оказаться выше FPS якоря; если не тяжелее — не может оказаться ниже. Изменения в разных направлениях несравнимы. Противоречивые якоря означают ошибку данных, а не повод выбрать удобное число.

Активные RT или upscale не наследуют эти native-проекции. Для них может существовать собственная точная scenario-строка, которая обрабатывается первой.

Полный ручной калиброванный путь можно сверять с `samples/site-manual-reference.json`. Для каждого case смотрите, сохранён ли успешный ответ или ошибка. Отличия от basic-reference ожидаемы и отражают выбор другого алгоритма.

Конкретный пример из комплекта: 007 First Light, RTX 5090, 1440p, stateId `663544`. В базовом режиме `220.9090909090909 × 0.8470045085935713` даёт GPU-лимит 187.11099598930713; при CPU-лимите 297 итог равен 187 FPS. Точная калибровка сайта заменяет GPU-лимит на 146.8 и даёт 147 FPS. Это два объяснимых результата разных режимов, а не погрешность округления.

## Source native профили

`fps_native_presets` — отдельный способ адресовать сценарий через `preset_id`. Его реальные `controls_json` могут не совпадать с прежними `game_settings`. Не создавайте такому профилю выдуманный stateId или индексный вектор.

Для общего качества и режима RT выбирается совместимый профиль. Сначала предпочтителен профиль с точной GPU/разрешение-ячейкой; затем первый совместимый по возрастанию preset_id. Проверяются разрешённые vendor/GPU, `requires_rtx`, аппаратная поддержка RT и `rendering_json`.

После выбора профиля точная строка `fps_native_preset_gpu_limits` или `fps_native_preset_cpu_limits` имеет приоритет. Без неё fallback-оценка ограничивается сопоставимыми якорями. Для GPU качество и число пикселей задают частичный порядок: более тяжёлый запрос не может быть быстрее более лёгкого точного якоря. Для CPU сравниваются качества в одном разрешении. Разные rendering domains и source-протоколы нельзя произвольно смешивать.

Финал учитывает оба cap: `floor(min(G, C, game.fps_cap, preset.fps_cap) + 0.5)`, где отсутствующий cap считается бесконечным. Профили с GPU/vendor/RTX/rendering scope сохраняют прежний vendorless CPU prior; GPU-ограничение не создаёт новое измерение CPU.

Порядок resolver важен: при явно выбранном source-native профиле fallback и native bounds обрабатываются отдельным путём, а не универсальной цепочкой «применить все калибровки подряд». Полное воспроизведение этого уровня требует отдельного набора проверок по profiles, scopes, rendering domains и anchor bounds. Ручной эталон calculateFps сам по себе не подтверждает эту часть.

## Откуда берётся уверенность в результате

Базовый фактор, экстраполяция, компонентный якорь и среднее всей тестовой сборки — разные виды данных. Среднее всей сборки само по себе не определяет независимо предел CPU и предел GPU. Исторические источники, настройки, разрешения и сведения о происхождении сохранены в companion JSON и source snapshots.

Сохраняйте `provenance_id`, точную игру, железо, разрешение и профиль рядом с калибровкой. Не переносите один результат на все VRAM-варианты, RT-режимы и GPU другого производителя. Не называйте оценку измерением конкретного компьютера студента.

## Как этот модуль связан с полной панелью сайта

Низкоуровневый ручной API `/api/v1/configurator/fps/calculate` принимает slug CPU/GPU и индексные настройки. Полная панель конфигуратора вызывает `/api/v1/configurator/workload-analysis` и передаёт UUID комплектующих всей сборки. Там дополнительно существуют проверка полноты сборки, профили workload, резервы CPU и статусы возможностей.

В каталоге готовых ПК также есть сохранённые PostgreSQL-снимки FPS для версий сборок. Они не нужны самостоятельному калькулятору. Для учебной задачи достаточно локальной SQLite и собственного API, а структура пользовательских действий может оставаться похожей на панель сайта.
